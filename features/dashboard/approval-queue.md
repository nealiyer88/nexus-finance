# Feature Brief: Approval Queue (API + Dashboard)

**Author:** Neal Iyer
**Date:** 2026-05-10 (rewritten against 10b; rewritten again against shipped 10a / 10c / 16)
**Status:** Approved
**Complexity:** L
**FP&A Phase:** 1 (Entity Resolution)
**Feature #:** 11

---

## Problem Statement

The matcher produces dispositions — some auto-approved, others queued for human review. Without an approval queue, the human-in-the-loop pattern doesn't exist. A Controller needs to see pending cross-category matches, understand why the system thinks they match (signal breakdown, LLM reasoning if applicable), and approve/reject/correct with one click. Every approval trains the graph and compounds institutional knowledge.

Until feature 10b, this feature was unbuildable: Stage 4's `Disposition` is an in-memory dataclass that nothing persisted, so `GET /approvals/pending` had no source of truth and the Stage 6 writers in `core/graph/resolution.py` had nothing to be reconstructed from. **Feature 10b (`features/pipeline/pending-decision-persistence.md`) closes that hole.** It ships the `pending_decisions` table in the live SQLite store, `core/matching/pending_store.py`, and — critically — a serialized snapshot (`entity_json` / `disposition_json` / `proposal_json`) that rehydrates into exactly the arguments the shipped Stage 6 writers demand. This feature is the human surface over that store, and it consumes 10b's contract **as 10b defines it**. It invents no table, no column, and no parallel schema.

**A deliberate scope choice, not a premise about the tree: features 10a and 10c are SHIPPED, and this feature still does not write `approval_decisions` or `audit_log`.** Those two tables are Postgres-side and belong to the Postgres store's own ownership boundary; recording decisions into them is explicitly out of scope here. What this feature records instead is 10b's own resolved-by / resolved-at / outcome columns on the SQLite pending row. The pending-decision store this feature is the surface over is SQLite by design (10b), and every read and write path in this feature therefore builds, runs, and is verified against SQLite alone — the approvals router opens no Postgres engine and names neither Postgres-side table. This is a scope boundary the build must hold, not an assumption about what exists.

## Scope

### In Scope

- **Fill in `api/routers/approvals.py`** — the file exists today as a docstring-only "Not yet implemented" stub. This is a fill-in, not a create. It declares an `APIRouter` and exposes:
  - `GET /approvals/pending` — list pending items for the resolved tenant, paginated, sorted by confidence descending. Backed by `pending_store.list_pending`, whose ordering contract (`top_score` descending, ties broken by ascending `pending_id`, honouring `limit` / `offset`) this endpoint inherits rather than re-implements. No secondary sort of its own.
  - `GET /approvals/{pending_id}` — one item with full context: signal breakdown, graph evidence, LLM reasoning when present, plus `created_at` so the UI can surface snapshot age (10b's named staleness tradeoff). Backed by `pending_store.get_pending`. Returns `404` when the id is absent **or** out of tenant scope — the two cases are indistinguishable to the caller by design.
  - `POST /approvals/{pending_id}/approve` — see the rehydration contract below. Dispatches to `resolve_match`, then `mark_decided(status='approved')`.
  - `POST /approvals/{pending_id}/reject` — dispatches to `reject_match`, then `mark_decided(status='rejected')`.
  - `POST /approvals/{pending_id}/correct` — the human supplies a canonical id. Dispatches to `resolve_match` with that id, then `mark_decided(status='corrected')`.
  - The status vocabulary is 10b's: `pending` (the initial state) plus the terminal `approved`, `rejected`, `corrected`. The build reads the permitted set out of 10b's shipped `CHECK` constraint at build time and asserts the statuses it writes are drawn from it, rather than trusting the transcription above.
  - Every route is idempotent against a decided row: because `mark_decided` is a one-way transition and 10b's rows are never deleted, a second POST against an already-terminal item returns `409` and performs no write.

- **Register the router in `api/main.py` — additively.** The registration is a new `include_router` call for **this feature's own** router, added alongside every router already registered there. No existing `include_router` call may be removed, rewritten, or reordered relative to another, and no middleware registration may be added, removed, or reordered by this feature. Whatever routers and middleware `api/main.py` already wires keep their wiring and their order exactly; this feature's edit is purely one additional line's worth of registration. Without it the endpoints exist at no URL, so the registration is a deliverable, not a nicety.

- **The rehydration contract — this is the load-bearing part of the feature.** An approval id is not enough to drive Stage 6; the shipped writers take a live `Disposition`, a live `NormalizedEntity`, and a set of write arguments that exist nowhere else. Each write path therefore:
  1. `get_pending(conn, pending_id, tenant_id)` — tenant-scoped, returning `None` when the row is absent or out of scope, which the route turns into `404`. The `conn` is the one yielded by the store module's connection provider (see Store Connection), never one the router constructed.
  2. `rehydrate(pending)` → `(Disposition, NormalizedEntity, proposal)` — 10b's pure function. This feature does not parse the JSON columns itself and does not reconstruct dataclasses of its own.
  3. Dispatch to the Stage 6 writer, passing the rehydrated triple plus the caller-supplied values that never live on the row: the connection, `reasoning_trace`, `tenant_id`, `approved_by` (the resolved actor) — passed **only** to writers whose signature actually accepts it, which on this feature's routed paths means `resolve_match` and never `reject_match`, whose signature has no such parameter and would raise on it — and, on the reject path only, `rejected_canonical_id`, which the proposal does not carry and the route supplies itself.
  4. `mark_decided(...)` with the terminal status, the actor, and the resulting canonical id.

  **Argument coverage is derived at build time, never transcribed.** The build reads `inspect.signature` of each writer as actually imported from `core.graph.resolution`, subtracts the caller-supplied names and every parameter carrying a default, and sources the remainder from the `proposal` dict. No parameter list, and no count of parameters, appears in this brief or in any code or test derived from it. This mirrors 10b's own signature-coverage criterion; if a writer gains a required parameter, both features fail loudly rather than silently mis-calling.

- **Per-path specifics that are not symmetric and must not be treated as such:**
  - **Reject.** `reject_match` raises `ValueError` when the rejected canonical id is absent from `disposition.candidates_ranked`. The route therefore validates membership against the **rehydrated** `candidates_ranked` first and returns `400` on a miss; a `ValueError` must never escape as a `500`. The default rejected id is the row's top candidate.
  - **Correct.** The human's canonical id replaces the top candidate throughout the write arguments, not just in the `canonical_id` slot: any `proposal` value that names the row's `top_canonical_id` is substituted with the human's id, located by comparing against `top_canonical_id` rather than by assuming which positional field holds it. The human's id is **not** required to appear in `candidates_ranked` — `resolve_match` does not validate membership, and a correction to an entity the matcher never surfaced is the whole point of the path.
  - **Approve.** Straight dispatch with the row's own top candidate; no substitution.
  - `create_new_entity` is **not** wired to a route in this feature. The `/correct` path resolves to an *existing* canonical id. A "none of these — create a new entity" flow is a separate correction mode and is out of scope.

- **Transaction ordering, stated because it is not what a reader would assume.** The Stage 6 writers in `core/graph/resolution.py` own their own transaction boundary — each one commits on success and rolls back on failure. `core/matching/pending_store.py` deliberately does neither. Consequently the writer's commit lands **before** `mark_decided`, and the two are not one transaction. The route therefore: dispatches the writer first, then issues `mark_decided` and commits it. The failure window is a resolved graph with a still-`pending` row — visible, and safe to re-drive because the Stage 6 writers are idempotent (a repeat inserts no duplicate alias and increments the existing edge's approval count instead of inserting a second edge). The inverse ordering — marking decided first — would produce a decided row with no graph mutation, which is silent and unrecoverable, and is forbidden.

- **Tenant scoping — consume the shipped middleware, resolve nothing locally.** `api/middleware/tenant.py` is shipped and working: feature 16's `TenantMiddleware` resolves a tenant per request (`X-Nexus-Tenant` header, else the `NEXUS_TENANT_ID` environment variable, else its `DEFAULT_TENANT_ID`, which is a binding to the Postgres bootstrap tenant constant rather than a literal typed into that module) and stamps it onto `request.state.tenant_id`. No row-level security exists anywhere in this project, no `CREATE POLICY` is written by this feature, and the word RLS does not appear in it. What ships instead:
  - **Every route reads `request.state.tenant_id`,** exactly as `api/routers/connectors.py` does — the shipped consumption pattern this feature copies rather than reinvents. The approvals router parses no tenant header, reads no tenant environment variable, and defines no fallback constant of its own. Header/env precedence is the middleware's contract, not this feature's.
  - **There is no "no resolvable tenant" case to handle, and this feature must not invent one.** The middleware always resolves a value — it falls back to `DEFAULT_TENANT_ID` — so `request.state.tenant_id` is never absent and never `None` by the time a handler runs. A malformed (non-UUID) tenant is rejected with `400` by the middleware *before* the handler is entered, so that rejection is neither implemented nor owned here. Any criterion demanding that this router return `400` for an unresolvable tenant would be unsatisfiable and is deliberately absent.
  - **Tenant ids used anywhere in this feature's tests must be UUID strings *generated at runtime*, never written as literals.** The middleware validates the header and the environment variable as syntactically valid UUIDs and short-circuits with `400` otherwise, so a fixture tenant like `"tenant-a"` never reaches a handler. Every fixture tenant is therefore produced by `str(uuid.uuid4())` at test time; a bare UUID literal must not be typed into any source file this feature touches, because a shipped test greps `api/`, `dashboard/` and `tests/` for exactly that pattern and would turn red. Two-tenant scoping fixtures use two separately generated, distinct values.
  - Every call into `pending_store` and into `core/graph/resolution.py` passes that resolved tenant explicitly. `pending_store` and `core/graph/entity_store.py` both apply no filter when `tenant_id` is `None` (the documented single-tenant SQLite default), so passing `None` would silently return unscoped rows. This feature never passes `None`.
  - Stated plainly, as feature 16 states it: this is **data shaping, not isolation**. The header is unauthenticated and any caller may assert any tenant. No code, test, comment, or criterion in this feature may describe the result as tenant isolation, RLS, multi-tenancy, or access control.

- **Fill in `dashboard/pages/approval_queue.py`** — the file exists today as a `dash.register_page` call plus an empty `html.Div` and a TODO. **Preserve its currently registered path and name exactly as the file declares them today**; feature 16's shell asserts that every page module registers at the path its own source declares and that pre-existing modules keep the path they had. Changing either breaks a downstream criterion this feature does not own. The body gains:
  - A `dash_table.DataTable` of pending items: incoming entity name, candidate entity name, source categories, confidence score, match type.
  - An expandable detail view: full signal breakdown, graph evidence, LLM reasoning when the item carries a Stage 5 assessment.
  - Approve / Reject / Correct actions per row.
  - Filters on `entity_category` (`organization` | `person`), confidence range, and category pair. Note the distinct fields on `NormalizedEntity`: `entity_category` is the person/organization axis this filter uses; `category` is the `accounting` | `psa` axis the "source categories" column displays. Do not conflate them.
  - A pure `apply_filters(rows, **filters) -> list[dict]` helper that performs the filtering, exercised directly on fixture rows — the same structure contract feature 16 uses for its pages, so filtering is testable without a browser or a running app.
  - A **pending-count helper** exposed at module level, returning the count for a resolved tenant. The page renders it as an in-page badge itself.

- **Build against feature 16's SHIPPED shell contract.** `dashboard/app.py` exists: it constructs the `dash.Dash` application with `use_pages=True` and builds its sidebar by iterating `dash.page_registry`, deliberately hosting no callbacks and no shared state. This feature is a page and a callback inside that shipped shell, and it edits the shell module not at all:
  - The page continues to call `dash.register_page` with the path and name its own source already declares, so the shell picks it up and links to it automatically with no edit to the shell.
  - **The page's layout must import and render with NO database present.** Importing `dashboard.pages.approval_queue` and building its `layout` must open no connection, run no query, and require no store file to exist. All data access happens inside callbacks, which the shell's page-render path does not invoke. Any module-level query would fail the shell's own live page-render test on a machine with no store, which is precisely the regression this rule exists to prevent.
  - **The reserved sidebar badge slot is CLAIMED by this feature.** The shell renders one badge slot per registered page, and the shipped shell test asserts that the slot for this page's path — the pattern-matching id `{"type": "nav-badge", "path": "/approval-queue"}` — is present in its layout. That slot is reserved for this feature and is empty until this feature fills it. This feature attaches the callback that populates that badge with the pending count for the resolved tenant, targeting that slot id, **without editing `dashboard/app.py`**. The callback is a deliverable, not a nicety.
  - The badge count itself comes from the module-level pending-count helper above, so the callback is a thin adapter over a helper that is directly testable without a browser or a running application.
  - **No regression to the shell's live render test.** Feature 16 ships a test that iterates the page registry and asserts every registered path returns `200` from a live test client. That test currently passes with this page registered, and it must still pass after this feature fills the page in. A layout that touches a database at import or layout-build time turns it red, which is the concrete failure this criterion guards.

- **Approval context display must show cross-category alias information:** "This RUDDR entity 'cenlar-fsb' may match QB entity 'Cenlar, LLC.' — here's why we think so." The raw, un-normalized names are available because 10b stores the `NormalizedEntity` unredacted, deliberately — see 10b's Privacy section. This feature must not redact, hash, or normalize away the names it exists to display.

- **Test suite `tests/test_approvals_api.py`** — pure SQLite, no database server, no network, no reachable Postgres, no browser. It builds its schema from files (`db/schema_sqlite.sql`, then the training migration, then 10b's pending-decisions migration located by glob, not by number), following the path-constant pattern the shipped test modules already use. Never `CREATE TABLE` inside a test. Two further fixture rules, both load-bearing: every tenant id it uses is a UUID string generated at runtime via `str(uuid.uuid4())` and never a literal, because the shipped tenant middleware `400`s a non-UUID before a handler runs *and* a shipped test forbids bare UUID literals under `api/`, `dashboard/` and `tests/`; and it points the store's path configuration at a per-test temporary file so the connection provider opens a throwaway store rather than a developer's real one.

### Store Connection — decided

This is settled; the build implements it and does not re-open it.

- **The pending-decision store is SQLite-backed by design.** That is feature 10b's deliberate choice, not an interim state and not a gap to be closed by moving `pending_decisions` to Postgres. This feature does not migrate the store, mirror it, or add a Postgres copy of any of its rows.
- **The API layer opens exactly one engine.** Feature 16 established the rule and the shipped API layer holds it: the Postgres engine, obtained through `core.graph.pg.connect()`. No module under `api/` constructs a SQLite connection. **Feature 11 does not reverse that rule.**
- **Therefore `core/matching/pending_store.py` gains a connection provider** — a module-level accessor exposed as a context manager that opens the store's own SQLite connection, yields it, and closes it on exit (including on an exception path). **No SQLite store-path convention exists anywhere in this tree today, so this feature defines the one it needs — decided here, not left to the builder.** The store module gains a module-level default-path constant `DEFAULT_STORE_PATH`, defaulting to `nexus.db` at the repository root (matching the `*.db` pattern the repo already ignores from version control), overridable by exactly one environment variable, `NEXUS_STORE_PATH`, read via `os.environ.get` in the naming style of the shipped `NEXUS_TENANT_ID`. That constant plus that single variable are the whole configuration: no second variable, no settings object, no CLI argument, no caller-passed path. Both the constant and the environment variable are **required deliverables of this feature**. Opening, configuring and closing that connection is the store module's job because the store module is what knows where the store is; every criterion below that speaks of "the store path configuration" means this constant and this variable.
- **The approvals router calls that accessor and nothing else.** `api/routers/approvals.py` does not `import sqlite3`, never calls `sqlite3.connect`, never accepts a connection from a caller, and never holds a connection open across requests. It enters the accessor per request, does its reads/writes and its `mark_decided` commit inside that scope, and exits. Dash callbacks in `dashboard/pages/approval_queue.py` obtain their connection the same way.
- This is a **required deliverable of this feature**, not an implementation detail left to the builder: the accessor ships in `core/matching/pending_store.py` as an addition beside 10b's existing functions, changing none of their signatures and changing no DDL. Because it adds a function rather than altering one, it does not violate the "modify nothing in 10b's contract" rule that governs the rest of this feature — nothing 10b ships behaves differently after it lands.
- The accessor resolves its path at call time, not at import time, so tests point it at a temporary store file per test and no test ever writes to a developer's real store.

### Out of Scope

- **The `pending_decisions` table, `core/matching/pending_store.py`, and the Stage 4 enqueue call — feature 10b.** This feature reads and transitions rows; it ships no DDL, no migration, and no `enqueue_pending` call site. Any change to 10b's schema or module signatures belongs to 10b.
- **A persisted audit log — out of scope by choice.** `api/middleware/audit.py` is shipped and real, and it is feature 16's middleware over the Postgres-side `audit_log`; this feature neither extends it, nor configures it, nor writes an audit row of its own, nor introduces a second audit surface. Whatever that shipped middleware records for a request it keeps recording, unchanged, with no involvement from this feature. What this feature *does* record for a decision is 10b's own resolved-by / resolved-at / outcome columns on the SQLite pending row (see V1 Hard Constraints).
- **Recording completed decisions into `approval_decisions` — out of scope by choice.** 10b's terminal `status` vocabulary already matches the `approval_decisions` `CHECK` set, so back-filling is mechanical whenever it is scheduled. It is not scheduled here: this feature writes no `approval_decisions` row and names that table nowhere.
- **The Dash application shell and the sidebar itself — feature 16, shipped.** This feature edits `dashboard/app.py` not at all. It *does* own the callback that fills the badge slot the shell reserved for its path (see In Scope); the slot's rendering, the sidebar's construction, and the badge id convention remain 16's.
- **Tenant middleware — feature 16, shipped.** This feature resolves no tenant of its own: it consumes `request.state.tenant_id`. It installs, edits and reorders no middleware, defines no `DEFAULT_TENANT_ID`, and implements no tenant-validation or tenant-rejection path.
- **Auth, roles, permissions, and any per-person visibility rule.** No auth exists anywhere in the tree; `api/routers/auth.py` is a stub and rules §0 marks auth `[PLANNED]`. Real login arrives with feature 17.
- **A create-new-entity correction mode.** `/correct` resolves to an existing canonical id only.
- Batch approve (approve all above threshold X) — V2.
- Email notifications for new pending items — uses Resend, deferred.
- Mobile-optimized approval UI.
- Approval delegation (assign to another user).

## Success Criteria

Every criterion below runs against SQLite alone, with **no reachable Postgres store and no browser**. The Postgres-side pieces the tree already ships are simply never exercised by anything this feature owns: no criterion here requires a Postgres connection to be openable, and every one of them must pass on a machine where opening one fails.

Tenant ids used in these criteria are UUID strings generated at runtime with `str(uuid.uuid4())`, never UUID literals typed into a source file — the shipped tenant middleware rejects a non-UUID with a `400` before a handler runs, so a non-UUID fixture tenant tests nothing this feature owns, and a shipped test forbids bare UUID literals anywhere under `api/`, `dashboard/` or `tests/`.

- [ ] `api/routers/approvals.py` declares an `APIRouter` whose registered routes, iterated off the router object itself, are exactly the `(method, path)` pairs named in Scope — asserted as a set equality against that named set, which is itself asserted non-empty so the equality cannot be satisfied by two empty sets.
- [ ] **The router is reachable:** after importing `api.main`, the set of `(method, path)` pairs contributed by the approvals router is non-empty, and is a subset of the pairs registered on `api.main.app` — both derived from the router object and from `app.routes` at test time, with no path list written into the test beyond the ones this feature owns. The non-emptiness assertion is required: a subset assertion alone passes vacuously against an empty router.
- [ ] **Registration is additive:** the set of `(method, path)` pairs registered on `api.main.app` before this feature is a non-empty proper subset of the set registered after it, and the middleware stack's classes *in order* are identical before and after — both "before" values captured from the pre-change revision at test time (the `api/main.py` at `HEAD`, e.g. via a checkout of that revision), never from a path list or middleware list transcribed into the test. The non-emptiness assertion on the "before" set is required, since a subset check alone would pass if the pre-change set were empty.
- [ ] `GET /approvals/pending` returns only rows for the resolved tenant: rows seeded under two distinct UUID tenants are each returned for their own tenant and never for the other, with both per-tenant result sets asserted non-empty, and the response order matches `pending_store.list_pending`'s ordering (`top_score` descending, `pending_id` ascending) for the same inputs — asserted over a seeded set containing at least one `top_score` tie, so the tiebreak is actually exercised rather than trivially satisfied.
- [ ] **The tenant comes from the middleware, not from the router:** a test asserts `api/routers/approvals.py` reads `request.state.tenant_id` and that its source contains no reference to the tenant header name, the tenant environment variable name, or a fallback tenant constant. Behaviourally: a request carrying an explicit `X-Nexus-Tenant` UUID returns that tenant's rows, and the same request with the header omitted (and the tenant environment variable unset) still succeeds — returning the middleware's default tenant's rows rather than an error — with the returned set asserted non-empty after seeding rows under that default tenant.
- [ ] **No unscoped call is possible:** a spy records every call this router makes into `core.matching.pending_store` and `core.graph.resolution`; the test asserts the recorded call list is non-empty and that every recorded call received a non-`None` tenant argument. Both halves are required — the per-call assertion alone passes vacuously if no call was recorded.
- [ ] `grep -rniE "\bRLS\b|CREATE POLICY|row.level security" api/routers/approvals.py dashboard/pages/approval_queue.py tests/test_approvals_api.py` returns no matches.
- [ ] **Approve drives Stage 6 for real, from the row alone:** a test seeds a `QUEUE_FOR_REVIEW` row via 10b's `enqueue_pending`, POSTs to `/approve`, and asserts the resulting `entity_aliases` and `entity_edges` state — both tables asserted to contain at least the specific row the writer should have produced, with its values compared field by field rather than merely counted or type-checked — proving the route reconstructed the writer's arguments from the snapshot with no pipeline in memory. The row's `status` is then terminal and its `resolved_by` / `resolved_at` are populated.
- [ ] **Argument coverage is derived, not enumerated:** the test first asserts the set of Stage 6 writers this router dispatches to is non-empty, then, for each, computes `inspect.signature(fn).parameters`, removes that writer's caller-supplied names — the connection, the rehydrated `disposition` and `entity`, `reasoning_trace`, `tenant_id`, `approved_by` for the writers whose signature accepts it, and `rejected_canonical_id` on the reject path — and every parameter carrying a default, then asserts each name remaining is sourced from the rehydrated `proposal`. The union of those remainders across the dispatched writers is asserted non-empty; both that assertion and the writer-set one are required, since the per-name loop proves nothing over an empty writer set or an all-empty union. A single writer whose remainder is empty after subtraction is permitted only because the non-empty union is proved separately. The test hardcodes no parameter names beyond the caller-supplied set and no counts.
- [ ] **Reject with a candidate the disposition does not contain returns `400`,** not `500`: the `ValueError` `reject_match` raises for an unknown canonical id never escapes the handler, and no row transitions.
- [ ] **Reject writes a negative training pair when — and only when — the item carries a Stage 5 call id.** Two asserted cases, both required: (a) an item whose rehydrated disposition carries an `LLMAssessment` with a `call_id` backed by a matching `llm_training_data` row increases the `llm_training_data` row count by one, with the rejected disposition value; (b) an item with no Stage 5 call id produces **zero** additional training rows — `SELECT COUNT(*) FROM llm_training_data` is unchanged across the call — and the route still returns success and still transitions the row to rejected. Case (b) is the common one: the queue's main population is the band above the LLM band, which never invokes Stage 5, plus abbreviation-rescue items that route around it by design. The documented no-write behavior is asserted explicitly so a later reader cannot mistake it for a bug.
- [ ] **Correct resolves to the human-supplied canonical id throughout:** a test corrects to an id that is *not* the row's top candidate and asserts the written alias and edge name the human's id — including every `proposal`-derived field that previously named `top_canonical_id` — and that the row transitions to the corrected status with that id recorded as its outcome.
- [ ] **A second POST against a terminal row returns `409` and writes nothing:** row count, `status`, `resolved_by` and `resolved_at` are all unchanged from the values captured after the first POST (compare before/after; never against a literal).
- [ ] **Ordering under mark-then-write failure:** a test forces the Stage 6 writer to raise and asserts the row is still `pending` (the writer rolled itself back and `mark_decided` was never reached), and a test that forces `mark_decided` to fail after a successful write asserts the graph mutation stands and the row is still `pending` — the documented, re-drivable window, not a silent loss.
- [ ] **The page's layout builds with no database present:** with the store path configuration pointed at a path that does not exist, importing `dashboard.pages.approval_queue` and building its `layout` raises nothing and produces a component — asserted by rendering the layout to its component tree and asserting the tree contains a non-empty set of component ids. No `except Exception` wrapper appears anywhere in this test; a raised exception must fail it.
- [ ] `dashboard/pages/approval_queue.py` exposes `layout` and its `dash.register_page` call declares the same path and name as the version in `git show HEAD:dashboard/pages/approval_queue.py` — asserted by comparing the two sources, so the shell contract cannot drift.
- [ ] **No regression to the shipped shell's live render test:** `.venv/bin/python -m pytest tests/test_dashboard_shell.py -x --tb=short` passes after this feature, including its test that iterates the page registry and asserts every registered path returns `200` from a live test client. That test is run against a machine with no store present, since a layout that queried at import or layout-build time would turn it red there and only there.
- [ ] **The reserved sidebar badge slot is populated by this feature's callback:** a test asserts that the application's registered callbacks include one whose output targets the pattern-matching id `{"type": "nav-badge", "path": <this page's registered path, read from the page module's own source>}`, that the set of callbacks matching that output is non-empty, and that invoking the callback's function against a seeded store returns the pending count for the resolved tenant. `dashboard/app.py` is byte-identical before and after this feature, asserted against `git show HEAD:dashboard/app.py`.
- [ ] The page's table exposes the columns named in Scope, and each filter named in Scope is asserted independently by calling `apply_filters` directly on fixture rows. Each filter's fixture input and its expected output are both asserted non-empty, and each filter case asserts at least one row is excluded — a filter that returns everything, or one exercised only against an empty row list, fails.
- [ ] Signal breakdown and graph evidence appear in the detail view for a fixture item; LLM reasoning appears for an item carrying an `LLMAssessment` and is absent (not empty-stringed, not `"None"`) for one that carries none.
- [ ] The raw, un-normalized names of both sides are present in the rendered detail output for a fixture item — locking in 10b's deliberate no-redaction stance for this table, so a later refactor cannot redact the queue into uselessness.
- [ ] The module-level pending-count helper returns a count matching `SELECT COUNT(*)` over 10b's pending rows for the same tenant, with that count asserted greater than zero for a seeded tenant, and is scoped: seeding an additional row under a second UUID tenant leaves the first tenant's count equal to its previously captured value.

## Estimated Complexity

**Rating:** L (raised from M)

**Rationale:** The original M rating called this "standard CRUD." It is not. The load-bearing work is **rehydration**: reconstructing, from a serialized snapshot owned by another feature, the exact argument set each shipped Stage 6 writer demands — derived at build time via `inspect.signature`, because transcribing it is precisely how this brief was wrong before. Around that sit asymmetries that each have their own failure mode: reject validates candidate membership and raises where approve does not; correct must substitute the human's canonical id through every proposal field that named the old one, not just the obvious slot; and the writers own their own commit, so `mark_decided` cannot be atomic with the graph mutation and the ordering had to be chosen for a recoverable failure window rather than for symmetry. Add a shipped shell whose seams must be met exactly rather than approximated (16's page-registration contract, its reserved badge slot, its `request.state.tenant_id` convention, and its live every-page-renders test, which a single module-level query would turn red), a connection provider that must be added to the store module because `api/` is not permitted to open a SQLite connection itself, and a negative-training-pair behavior that is correct precisely when it writes nothing. The dashboard work itself — DataTable, expandable rows, a pure filter helper — is the least risky part of the feature.

### Implementation Notes (constraints for the build)

1. **Every test command is `.venv/bin/python -m pytest ...`.** Bare `pytest` is not on PATH, and `.venv/bin/pytest` does not put the repo root on `sys.path`, so every `from core...` import fails to collect.
2. **A criterion that only checks an exit code is not a criterion.** Assert on the reported collected count.
3. **Both target files already exist.** `api/routers/approvals.py` is a docstring-only stub; `dashboard/pages/approval_queue.py` is a `register_page` call plus an empty `Div` and a TODO. Fill them in; preserve the page's registered path and name.
4. **Derive, do not transcribe.** Stage 6 argument sets come from `inspect.signature`; 10b's status vocabulary from its shipped `CHECK` constraint; 10b's migration from a glob, not a number; the page's registered path from its own source at `HEAD`. Nothing about the tree's current state is written into this brief as a number.
5. **Cite symbols, not coordinates.** Every fact this brief asserts about the tree is a symbol name, a docstring phrase, a DDL constraint, or a grep — never a file-and-line coordinate, never a count. Upstream features land between briefing and build.
6. **The Stage 6 writers commit; `pending_store` does not.** Write first, mark second. Do not "fix" the asymmetry by making `pending_store` commit — that is 10b's deliberate contract and changing it is out of this feature's ownership.
7. **Tenant ids are UUIDs, everywhere, including in fixtures — and they are generated, not written down.** The shipped middleware validates the header and the environment variable as UUIDs and short-circuits with `400`; a fixture tenant like `"tenant-a"` never reaches a handler and tests nothing. Produce every fixture tenant with `str(uuid.uuid4())` at test time; never type a UUID literal into a source file, which a shipped test greps for under `api/`, `dashboard/` and `tests/`. Two-tenant scoping fixtures use two separately generated, distinct values.
8. **`api/` opens one engine, and it is not SQLite.** The approvals router gets its SQLite connection from the store module's connection provider and constructs none itself. Do not "simplify" this by calling `sqlite3.connect` in the router — that reverses a rule feature 16 established and this feature explicitly upholds.
9. **The page's layout must not touch a database.** Data access lives in callbacks. A module-level or layout-time query fails the shipped shell's live every-page-returns-200 test on any machine without a store, which is the exact regression this rule prevents.
10. **A criterion that counts or compares must also assert non-emptiness.** Every subset check, every loop over a derived set, and every "all calls had X" assertion in this feature's tests is paired with an assertion that the set being checked is non-empty; otherwise it passes on an empty pipeline and proves nothing.
11. **Reject's silence is the specified behavior, not a bug.** Most queue items have no Stage 5 call id and their rejection writes no training pair. Assert it; do not work around it by writing an ungated pair, which would be a behavior change to shipped feature 10.

### V1 Hard Constraints (status-marked per `.claude/rules/01-nexus-finance-v1.md` §0)

- `[BUILT]` **SQLite is the only engine this feature touches.** The queue reads and transitions 10b's `pending_decisions` rows in the SQLite store, through the store module's own connection provider. This feature opens no Postgres connection, names no DSN, and imports no driver — a scope boundary, not a claim that no Postgres engine exists in the tree.
- `[BUILT]` **Every query carries an explicit tenant scope, taken from `request.state.tenant_id` as set by the shipped tenant middleware.** This replaces the former "every endpoint RLS-scoped to tenant_id" constraint, which was unverifiable: no policies exist. It also replaces the former "a request with no resolvable tenant is rejected" constraint, which is unsatisfiable: the middleware always resolves a tenant (falling back to `DEFAULT_TENANT_ID`) and rejects malformed ones itself, before any handler here runs. This is data shaping, not isolation — see Scope.
- `[BUILT via 10b]` **Who resolved an item and when is recorded** on the pending row itself, via `mark_decided`'s resolved-by / resolved-at / outcome columns. A **persisted, append-only audit log is out of scope by choice** — the shipped audit middleware writes to the Postgres-side `audit_log`, and this feature neither extends it nor adds a second audit surface.

Both branches are asserted.

- `[BUILT via 16]` The Dash application shell, sidebar navigation, the reserved per-page badge slot, and tenant middleware. Consumed here as shipped and edited nowhere; **the live sidebar badge for this page's slot is filled in by this feature's callback**, which is the one piece of that surface 16 left for this feature to claim.
