## Behavioural specification

Routes on the `APIRouter` in `api/routers/approvals.py`:
- `GET /approvals/pending` — pending items for the resolved tenant, paginated, backed by `pending_store.list_pending`, inheriting its ordering contract. No secondary sort of its own.
- `GET /approvals/{pending_id}` — one item with signal breakdown, graph evidence, LLM reasoning when present, and `created_at`. Backed by `pending_store.get_pending`. Returns `404` when the id is absent **or** out of tenant scope — indistinguishable to the caller by design.
- `POST /approvals/{pending_id}/approve` — rehydrate, dispatch `resolve_match` with the row's own top candidate (no substitution), then `mark_decided(status='approved')`.
- `POST /approvals/{pending_id}/reject` — validate the rejected canonical id's membership in the **rehydrated** `candidates_ranked` first and return `400` on a miss (a `ValueError` must never escape as a `500`); default the rejected id to the row's top candidate; dispatch `reject_match` (**never** passing `approved_by`), supplying `rejected_canonical_id` itself since the proposal does not carry it; then `mark_decided(status='rejected')`.
- `POST /approvals/{pending_id}/correct` — the human supplies a canonical id; substitute it for **every** `proposal` value that equals the row's `top_canonical_id`, located by comparing against `top_canonical_id` rather than by assuming which field holds it; dispatch `resolve_match`; then `mark_decided(status='corrected')`. The human's id is **not** required to appear in `candidates_ranked`.
- A second POST against an already-terminal row returns `409` and performs no write.
- `create_new_entity` is **not** wired to any route.

Each write path: `get_pending` (tenant-scoped, `None` → `404`) → `rehydrate(pending)` → dispatch the writer with the rehydrated triple plus the caller-supplied values (connection, `reasoning_trace`, `tenant_id`, `approved_by` only where the signature accepts it, `rejected_canonical_id` on reject only) → `mark_decided(...)` and commit it.

**Transaction ordering — write first, mark second.** The writer commits before `mark_decided`; they are not one transaction. The failure window is a resolved graph with a still-`pending` row: visible and safe to re-drive, because the Stage 6 writers are idempotent. The inverse ordering is forbidden, and you must not "fix" the asymmetry by making `pending_store` commit — that is 10b's deliberate contract.

The dashboard page gains: a `dash_table.DataTable` of pending items (incoming entity name, candidate entity name, source categories, confidence score, match type); an expandable detail view (full signal breakdown, graph evidence, LLM reasoning when the item carries a Stage 5 assessment); approve/reject/correct actions per row; filters on `entity_category` (`organization` | `person`), confidence range, and category pair; a pure `apply_filters(rows, **filters) -> list[dict]` helper; and a module-level pending-count helper returning the count for a resolved tenant. Note the distinct `NormalizedEntity` fields: `entity_category` is the person/organization axis the filter uses; `category` is the `accounting` | `psa` axis the "source categories" column displays — do not conflate them. The page attaches the callback populating the reserved badge slot `{"type": "nav-badge", "path": "/approval-queue"}` **without editing `dashboard/app.py`**; the badge count comes from the module-level helper. The detail view shows raw, un-normalized names of both sides — do not redact, hash, or normalize them away.
