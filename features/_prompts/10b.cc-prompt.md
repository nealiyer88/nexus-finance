### Table shape (`pending_decisions`)

| Column | Purpose |
|---|---|
| `pending_id` TEXT PRIMARY KEY | `"pending:" + uuid4().hex` |
| `tenant_id` TEXT | nullable |
| `decision_key` TEXT NOT NULL UNIQUE | idempotency key |
| `status` TEXT NOT NULL DEFAULT `'pending'` | CHECK IN (`'pending'`,`'approved'`,`'rejected'`,`'corrected'`) — same vocabulary as 10a's `approval_decisions.disposition` CHECK plus `'pending'` |
| `source_entity_id` TEXT NOT NULL | `Disposition.source_entity_id` |
| `action` TEXT NOT NULL | the `Action` value at enqueue time |
| `top_canonical_id` TEXT | `top_match.canonical_id`, NULL when `top_match` is None |
| `top_score` REAL | `top_match.score`, NULL when `top_match` is None |
| `category_pair` TEXT NOT NULL | `f"{a}:{b}"` |
| `cluster_conflict` INTEGER NOT NULL DEFAULT 0 | 0/1 |
| `abbreviation_rescue` INTEGER NOT NULL DEFAULT 0 | 0/1 |
| `llm_call_id` TEXT | `llm_assessment.call_id` or NULL — join key into `llm_training_data` |
| `entity_json` TEXT NOT NULL | serialized `NormalizedEntity` |
| `disposition_json` TEXT NOT NULL | serialized `Disposition` |
| `proposal_json` TEXT NOT NULL | pipeline-derived Stage 6 write arguments |
| `created_at` TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP | |
| `resolved_at` / `resolved_by` / `outcome_canonical_id` | NULL until a terminal transition |

Plus indices on `(tenant_id, status)` and `(status, top_score)`. **No foreign key on `top_canonical_id`** — the graph tables cascade on delete and a pending row is decision history that must not vanish; this divergence from the graph tables' FK style is deliberate.

### Module API

- `PendingDecision` — frozen dataclass mirroring the table columns, with the three JSON columns exposed as already-parsed objects.
- `enqueue_pending(conn, disposition, entity, proposal, tenant_id=None) -> Optional[str]`
- `list_pending(conn, tenant_id=None, limit=..., offset=...) -> list[PendingDecision]` — `status = 'pending'` only, ordered by `top_score` DESC then `pending_id` ASC.
- `get_pending(conn, pending_id, tenant_id=None) -> Optional[PendingDecision]`
- `rehydrate(pending) -> tuple[Disposition, NormalizedEntity, dict]` — pure function, no `conn`.
- `mark_decided(conn, pending_id, status, resolved_by, outcome_canonical_id=None, tenant_id=None) -> None` — one-way terminal transition. Never deletes.

### Enqueue gate

Write a row **only** when `disposition.action == "QUEUE_FOR_REVIEW"`. Every other member of the `Action` alias returns `None` and writes nothing. Derive the accepted-action set from the `Action` alias at build time.

### Rehydration

The row stores a **serialized snapshot, not an id-addressed reference** — nothing in any shipped table persists a `ScoredMatch`, so there is no id to dereference.

- `disposition_json` is `json.dumps(..., sort_keys=True)` over the full `Disposition`, including every element of `candidates_ranked` with its complete `signal_breakdown` (nested `b_boosts` entries included) and `graph_evidence`, plus `llm_assessment` when present.
- `entity_json` is the serialized `NormalizedEntity`, `raw_record` included.
- `proposal_json` carries the pipeline-derived Stage 6 write arguments recoverable from neither of the above — the edge shape, `alias_confidence`, the `system_refs` tuple for the new-entity path, and **whatever else `inspect.signature` shows is required**. Derive the full key set from the live signatures of `resolve_match` / `create_new_entity` / `reject_match`, not from this list.
- Tuples serialize as lists and **must** be restored as tuples so the frozen dataclasses compare `==` to the originals. `NormalizedEntity.rules_applied` is the exception — restore it as a `list`.
- `approved_by`, `reasoning_trace`, `conn` and `tenant_id` are supplied by the approving caller at decision time, never by the row.

### Privacy (deliberate divergence from the training path)

`entity_json` stores the **raw, unredacted** `NormalizedEntity`, `raw_record` included. **No `redact_org` / `redact_person` call, no `leak_check` gate.** The approval queue's entire product purpose is to show a human the real names; a redacted pending row is a useless pending row. Feature 10's "raw entity pairs are never stored" rule applies to the training corpus and does not apply to `pending_decisions`.

The countervailing guards are containment, not redaction: `pending_decisions` is never a training source — `core/matching/training_data.py` must not read it and `pending_store.py` must not write to `llm_training_data`, both directions grep-asserted in the test file.

### Idempotency

`decision_key = sha256(f"{tenant_id}|{entity.source}|{entity.source_id}|{top_canonical_id or ''}")` — deliberately excluding scores, timestamps and the candidate list.

> **For a given `decision_key` there is at most one row, ever.** Re-running the pipeline over the same entity with the row still `pending` refreshes `disposition_json` / `proposal_json` / `top_score` / `action` in place and returns the **existing** `pending_id`. Re-running it after the row has reached any terminal `status` writes nothing, mutates nothing, and returns `None`.

Enforce with the `UNIQUE (decision_key)` constraint plus a `SELECT`-then-branch inside `enqueue_pending`. **No `INSERT OR REPLACE` anywhere in the module** — it would silently discard a terminal row's `resolved_by` and `resolved_at`.

### Tenant scoping

`enqueue_pending` writes `tenant_id` as a real, nullable column value (never NOT NULL, never FK'd — no `tenants` table exists in SQLite). `list_pending`, `get_pending` and `mark_decided` apply `AND tenant_id = ?` when a tenant is passed and no filter when it is `None`. When a pending row names a `top_canonical_id`, `enqueue_pending` verifies that canonical is in tenant scope by calling `core/graph/entity_store.py`'s existing private tenant-scope assertion. No `CREATE POLICY`, no row-level security.
